# v5.1.3-dojobay.11

6.0.0 Release Candidate 1 (RC1). Explorer settings gain
mempool.onion beside the paired Dojo, the Block Explorer row
tells a timeout from a refusal, and one failing XPUB no longer
wipes its siblings. Every onion load stays on Tor. 13 PRs since
v5.1.3-dojobay.10; 3 issues closed.

## Fixed since v5.1.3-dojobay.10

### Explorer settings (#537)

- Settings > Explorer lists Paired, mempool.onion, mempool.space,
  and Custom, in that order (#537, following #512). mempool.onion
  is the existing onion host, http only. It can be selected only
  while Tor is ready; otherwise the row stays visible, greyed,
  with Needs Tor. Lookups for that host load over Tor and are
  blocked when Tor is off, with no direct fallback. Testnet uses
  the same `/testnet` path as the clearnet site. Paired shows
  "Your Dojo · onion" and the shortened onion when a Dojo
  explorer is bound.
- Each option has an info button that opens a sheet and does not
  change the selection. The mempool.onion sheet shows the full
  onion address so it can be checked. A blocking advisory is
  shown for mempool.onion, mempool.space, a clearnet Custom URL,
  and Analyze externally. It includes "Don't show again for this
  option" and is shown again if that route gets worse, for
  example when Tor goes off. An onion Custom URL does not get
  that advisory. The Tor/IP line follows the load decision for
  that URL. The mempool.space Tor sentence says the exit relay
  and mempool.space can see the lookup, and that the IP address
  stays hidden.
- An existing mempool choice stays the clearnet site. The paired
  Dojo explorer stays the default, and a Dojo-published clearnet
  explorer still does not bind (SR-23). The shared onion label
  keeps 7 head characters and 4 tail characters (7+4). Analyze
  externally still says am-i.exposed fetches the mempool.space
  API and bypasses the paired explorer, and it does not point at
  Dojo, Custom, or Settings.
- The Community Dojo list keeps version, jurisdiction, and
  online or offline, then that Dojo's block explorer only when
  its host ends in .onion (#540). The pairing onion stays off
  that line. The explorer onion goes through the same 7+4
  formatter. A clearnet explorer shows no address. A node with
  no explorer shows no onion.

### Block Explorer row (#520, #527, #523)

- The probe reads and closes its response off the main thread
  (#520 via #532). A 200 whose body is still on the socket is
  no longer drained on the main thread, so that close is no
  longer reported as Unreachable over Tor.
- A timeout or any other non-answer is amber "Could not confirm"
  (#527 via #536). Red "Unreachable over Tor" is only a refused
  connection, a SOCKS host-unreachable, or a non-2xx on both
  probe paths (`/api/blocks/tip/height` and the root).
- While the screen is open and the row is not green, the check
  retries after about 10s and then about 30s, twice at most, and
  never restarts a probe that is already running. A new Tor
  SOCKS generation resets that count. A timeout is remembered
  for 15s instead of 3 minutes. The check starts in onStart and
  the in-flight probe is cancelled in onStop.
- Checking shows "Checking… 12s", counting up once a second. A
  tappable row shows "Tap to retry". The operator name still
  appears only on a green paired row. Lookups are unchanged:
  the paired Dojo explorer stays the default, and the row
  status does not block them.
- A release build keeps one ExplorerProbe result line per probe
  (#523 via #536): shortened onion, outcome, HTTP status or
  exception class, and elapsed milliseconds. No query string,
  full onion, or exception message.

### Onion loads stay on Tor (SR-24)

- Any host ending in .onion requires Tor, not only
  mempool.onion (#472 via #539). A Custom onion URL is blocked
  when Tor is off, with the existing "Tor is required" dialog
  and no direct fallback. The same check runs for every later
  main-frame navigation and redirect. A subresource aimed at an
  onion host in a direct session is answered locally, so that
  host is not given to the system resolver. A WebView that
  started on a direct load cannot fetch an onion later, even
  after Tor is started on that screen. A WebView that started
  on the Tor proxy does not fall back to a direct load when Tor
  drops.
- Paired explorer, mempool.onion, mempool.space, and clearnet
  Custom keep their advisories. mempool.onion still loads only
  over Tor.

### Sync honesty (#522, #530)

- A Dojo status "error" envelope no longer aborts the whole
  round (#522 via #531). It throws DojoApiError, a real
  Exception, so the round counts that collection and continues.
  The banner is the partial-failure line, not "Sync
  interrupted." The regression suite pins the throw, both
  orders, and the healthy sibling (#534).
- DojoApiError carries only the fixed text "Dojo returned an
  error" (#522 via #539, SR-25). The server's error text is not
  copied into the throwable: that text can carry an XPUB or an
  onion, and a release dump keeps the throwable.
- One XPUB's failure no longer abandons the rest of the
  collection (#530 via #538). Each pub is fetched on its own.
  When one fails, the others are written, and the failed pub's
  existing transactions, UTXOs, and do-not-spend marks are
  handed to the reconcile as a keep-set. Its balance is left as
  it was. The collection comes back indeterminate, so the round
  counts it failed. If every pub fails, the first failure is
  thrown before that reconcile. ApiNotConfigured still aborts
  the collection with no reconcile. A real cancellation still
  propagates.
- A soft failure takes the same keep path (SR-26 via #541): a
  non-2xx response, a null body, or a body that is not JSON or
  not a wallet. A sibling that synced can no longer delete the
  soft-failed pub's transactions and UTXOs. A status "error"
  envelope is still DojoApiError with the fixed local message.
  Logs stay on the collection id, the pub index, and the HTTP
  code. They do not include the body, the URL, or the XPUB.
  #541 also repairs the master unit test that still expected
  the server's error text after SR-25.
- Failures are no longer rethrown as
  `CancellationException(e.message)` (#530 via #538). Exchange
  fetches and pairing rethrow the real exception. The
  do-not-spend store, the crash log, and send compose log and
  degrade. Sweep lets the real exception reach the existing
  outer catch. `SentinelState.refreshCollection` and
  `TransactionsViewModel.fetch` had no callers and are gone
  (#485 via #538).

### PIN screen (#528)

- Confirming exit leaves the app (#528 via #535). The exit
  prompt calls `finishAndRemoveTask()`, so a PIN screen stacked
  over an unlocked activity does not reveal that activity.
  Every `CLEAR_TASK` intent also sets `NEW_TASK`: unlock to
  Home, the unadmitted-session bounce, the idle-timeout bounce,
  the network switch, settings restart, backup import, and
  erase-all. Android ignores `CLEAR_TASK` without `NEW_TASK`.
- When saved unlock data cannot be opened, the pad shows that
  message in red. There is no wrong-PIN cross, because the PIN
  was not checked. A wrong PIN still flashes the cross and
  "Incorrect PIN". The unlock latch drops on every path that
  stays on the screen. A debug build logs the result name only,
  never the PIN. The PIN pad stays FLAG_SECURE. Admission is
  unchanged.

### Explorer log privacy (#521)

- The explorer WebView swallows page console messages (#521
  via #526). With no chrome client, Chromium wrote every
  console line to logcat with the full page URL: the Dojo
  explorer's onion and the viewed txid. `onConsoleMessage`
  returns true and nothing is re-logged. The same host covers
  the paired onion, Custom, mempool.space, mempool.onion, and
  am-i.exposed.

### Dependencies

- jackson-databind and jackson-datatype-jsr310 2.13.x -> 2.23.0,
  commons-lang3 -> 3.22.0 (#529), on Gradle and the extlibj
  pom. That retires the open jackson and commons-lang3
  Dependabot alerts.
- org.json -> 20260814 (#533), retiring GHSA-ghc9-756g-vrcv.
  On Android the runtime org.json still comes from the
  platform; the bump is the extlibj compile classpath and the
  unit-test classpath.

## Worth a specific check

1. Settings > Explorer shows Paired, mempool.onion,
   mempool.space, Custom. With Tor ready, mempool.onion warns,
   then a transaction loads the onion over Tor, including
   `/testnet` on testnet, and never the clearnet site. With Tor
   off the row is greyed Needs Tor and does not load (#537).
   Info opens a sheet, does not change the selection, and the
   mempool.onion sheet shows the full onion. The shortened
   label is 7 characters, an ellipsis, and 4 characters.
2. A Dojo that publishes a clearnet explorer still does not
   bind (SR-23). An existing mempool.space choice stays
   clearnet. Analyze externally still names am-i.exposed and
   the mempool.space API, and does not point at Dojo, Custom,
   or Settings.
3. Custom onion with Tor off is blocked with "Tor is required"
   and does not open in the clear (SR-24, #539). A clearnet
   page's link, redirect, or embedded onion subresource does
   not resolve. Turning Tor on inside that same screen does not
   allow the onion; close and reopen to load it over Tor.
   Turning Tor off after mempool.onion loaded does not fall
   back to a direct load.
4. Open Network just after Tor starts. The Block Explorer row
   shows amber "Checking… 12s" and "Tap to retry". A timeout is
   "Could not confirm", not red "Unreachable over Tor". It
   retries after about 10s, then about 30s, then stops. A
   refused connection, or non-2xx on both probe paths, is red.
   A 2xx is green "Bound to …" with the operator name and no
   "Tap to retry". Leaving the screen cancels the probe
   (#520, #527, #536). On a release build, `adb logcat -s
   ExplorerProbe` is one result line: shortened onion, outcome,
   status or exception class, elapsed time. No full onion
   (#523).
5. One collection, two XPUBs, one the Dojo rejects (status
   error, HTTP 500, or an empty body) and one it accepts. The
   accepted XPUB updates. The rejected XPUB keeps its previous
   balance, transactions, UTXOs, and do-not-spend mark. The
   banner is not "Sync interrupted." and the server's error
   sentence is not shown (#522, #538, #541, SR-25, SR-26).
6. PIN: a wrong PIN shows the red cross. Back, then confirm,
   exits to the launcher and Recents is clean. A PIN screen
   stacked over an unlocked activity does not reveal it. After
   the idle timeout, unlocking lands on a single Home. A
   screenshot of the PIN pad is still blocked (#528, #535).
7. Open a transaction in the explorer on a release build.
   `adb logcat` shows no chromium `[INFO:CONSOLE]` line with
   the onion or the txid (#521). The same for am-i.exposed.
8. The Community Dojo list shows the shortened block explorer
   onion, and shows no address for a clearnet explorer or the
   pairing onion (#540).
